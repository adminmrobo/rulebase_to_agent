01

쓸수록 나아지는 에이전트

헤르메스 에이전트는 오픈소스 AI 연구 집단 누스 리서치(Nous Research)가 2026년 공개한 MIT 라이선스 에이전트입니다. 공식 저장소는 스스로를 "학습 루프가 내장된 자가개선 AI 에이전트"라고 소개합니다. 경험에서 스킬을 만들고, 쓰면서 다듬고, 알아 둘 것을 스스로 기억에 남기고, 지난 대화를 검색하고, 사용자에 대한 이해를 세션을 넘어 쌓는다는 것입니다.출처: NousResearch/hermes-agent 저장소 README

공개 이후 빠르게 퍼졌습니다. 국내 커뮤니티 정리 글은 2026년 4월 기준 GitHub 별 7만 2천 개를 넘겼다고 전했고, AI타임스는 최근 30일 신규 기여자 수에서 먼저 나온 오픈소스 에이전트 OpenClaw를 앞질렀다고 보도했습니다. 그 보도는 성장 이유로 모델 자체보다 모델을 감싸는 하네스의 최적화를 꼽았습니다.출처: GPTers(2026.4) · AI타임스(2026), 「헤르메스, 신규 기여자 수에서 오픈클로 역전…'하네스' 최적화의 승리」

수치는 시점을 함께 보세요. 별 수는 하루가 다르게 바뀝니다. 위의 7만 2천 개는 2026년 4월 기준이고, 한 달 뒤 엔비디아를 인용한 개발자 매체 보도는 공개 석 달이 안 돼 14만 개를 넘겼다고 전했습니다(DEV Community, 2026.5.14). "신규 기여자 수 역전"도 AI타임스 보도 시점의 최근 30일 기준입니다. 최신 값은 GitHub 저장소(NousResearch/hermes-agent)에서 직접 확인하세요.
용어 정리. 개요를 짤 때 "헤르메스 엔지니어링"이라는 말을 썼지만, 이는 아직 표준 용어가 아닙니다. 이 장에서는 헤르메스를 자가개선 루프의 대표 사례로 다룹니다. 특정 제품의 기능 소개가 목적이 아니라, 2편에서 본 원리들이 한 시스템에 어떻게 모이는지 보려는 것입니다.
02

헤르메스 해부: 2편의 부품이 다 있다

공식 문서에 적힌 기능을 2편의 장별로 나눠 보면, 지금까지 본 부품이 거의 그대로 들어 있습니다.

2편의 부품헤르메스에서는
1장 에이전트 모델특정 모델에 묶이지 않음. 여러 모델 제공처 중에서 명령 한 줄로 바꿔 끼움. 모델을 바꿔도 기억·스킬·작업 흐름은 그대로
2장 하네스로컬·Docker·SSH 등 여섯 가지 실행 환경, 위험한 명령은 사람 승인, 파일 쓰기 제한, 컨테이너 격리, 프로젝트 파일 속 프롬프트 인젝션 탐지 등 8겹 보안
2장 컨텍스트에이전트 메모(MEMORY.md, 2,200자)와 사용자 프로필(USER.md, 1,375자)을 세션 시작 때 시스템 프롬프트에 넣음. 지난 대화는 검색해서 필요할 때만 꺼냄
3장 루프자연어로 정하는 예약 실행(일일 보고서, 주간 점검 등). 텔레그램·디스코드·슬랙 등 메신저로 결과 전달
4장 오케스트레이션격리된 서브에이전트를 띄워 병렬 작업. 여러 단계를 파이썬 스크립트 한 번으로 묶어 메인 컨텍스트를 아끼는 방식
5장 자가개선복잡한 일을 마친 뒤 스킬을 스스로 만들고, 쓰면서 다듬음. 스킬은 공개 표준(agentskills.io) 형식
출처: NousResearch/hermes-agent README, 문서 "Persistent Memory", "Security" · 위키독스 「Hermes Agent: 성장하는 AI 에이전트 실전 가이드」 01-2
조수(하루)기억 파일에 글자 수 한도가 있네요? 2,200자면 생각보다 짧아요.
박사2장의 배낭 문제야. 기억이 무한하면 컨텍스트 창이 넘치고 가운데가 흐려지지. 그래서 한도를 두고, 넘치면 에이전트가 스스로 합치거나 지워서 자리를 만들게 했다고 문서에 적혀 있어. 무엇을 남길지 고르는 것 자체가 학습인 셈이지.
03

닫힌 학습 루프

헤르메스를 다른 에이전트와 가르는 것은 일을 마친 뒤에 일어나는 일입니다. 웹 검색, 메일, 메신저처럼 여러 도구를 써야 하는 복잡한 일을 성공적으로 끝내거나 시행착오 끝에 해법을 찾으면, 그 과정을 작업 매뉴얼인 "스킬"로 문서화해 저장하고 다음에 같은 일이 오면 꺼내 씁니다.출처: AI타임스(2026) · 브런치, 「OpenClaw VS Hermes Agent」(2026.4)

스킬t ← 스킬t + 다듬기( 이번 결과 − 스킬이 예상한 결과 )
1편 4장의 Q ← Q + α[실제 − 예상]과 같은 모양입니다. 3장의 Reflexion이 "한 번의 일 안에서" 반성 메모를 썼다면, 헤르메스의 스킬은 날과 세션을 넘어 쌓입니다.
04

직접 보는 스킬 서랍

주판봇이 90일 동안 매일 반복 업무 8가지 중 하나를 맡긴다고 합시다. 스킬이 없으면 매번 55% 확률로 성공하고 비용은 10이 듭니다. 스킬이 있으면 숙련도 q에 따라 성공률이 55% + 40%×q까지 오르고 비용은 줄어듭니다. 그런데 실패한 일 중 30%는 겉보기에 "된 것 같아" 보입니다. 날짜를 움직여 서랍을 들여다보세요.

교훈 1

스킬은 시간을 산다

스킬이 쌓이자 성공률이 오르고 비용은 절반 아래로 떨어졌습니다. 1편 7장에서 "생각하는 시간"을 늘려 성능을 샀다면, 스킬은 지난번에 생각한 것을 재사용해 시간을 아낍니다.

교훈 2

검증 없이 저장하면 나쁜 습관이 굳는다

"된 것 같은" 실패까지 스킬로 저장하면, 8개 중 평균 1.7개가 잘못된 매뉴얼로 굳어 그 일은 오히려 스킬이 없을 때보다 못해집니다(성공 35%). 3장의 거짓 완료가 기억 속에 영구히 남는 셈입니다.

교훈 3

실패 분석이 서랍을 청소한다

검증을 통과한 것만 저장하고, 실패하면 원인을 붙여 고치거나 틀린 스킬을 버리자 90일 뒤 성공률이 93.2%까지 올랐습니다. 학습 루프의 질은 저장보다 버리기에서 갈립니다.

06

"저장했어요"를 믿지 마라

교훈 2가 지어낸 걱정만은 아닙니다. 헤르메스의 기억 문서에는 "기억하라고 말했는데 다음 세션에서 잊었다"는 문제를 다루는 절이 따로 있습니다. 첫 번째 점검 항목은 이것입니다.

기억은 모델이 기억 도구를 실제로 호출했을 때만 남습니다. "기억에 추가했습니다" 같은 문장은 그냥 글일 뿐입니다. 파일을 열어 그 내용이 있는지 확인하세요. 대략 300억 파라미터보다 작은 로컬 모델이나 도구 호출이 약한 모델은 도구 호출 없이 확인 문장만 쓰는 경우가 잦습니다.출처: Hermes Agent 문서 "Persistent Memory"의 문제 해결 절을 요약·번역

3장에서 루프가 "다 됐어요"를 믿으면 안 됐듯이, 자가개선 루프는 "저장했어요"를 믿으면 안 됩니다. 그래서 헤르메스는 기억 쓰기를 사람이 검토한 뒤에만 반영하는 설정, 그리고 예약 실행처럼 사람이 없는 세션에서 위험한 명령을 만나면 거부할지 허용할지 따로 정하는 설정(문서 예시는 거부)을 둡니다. 사람이 보지 않는 시간일수록 문지기는 더 엄격해야 한다는 2장과 3장의 원칙 그대로입니다.출처: Hermes Agent 문서 "Persistent Memory", "Security"

초파리 연구원결국 자가개선 루프의 핵심 부품은 "개선"이 아니라 "검증"이네. 무엇을 배울지 정하는 심판이 바깥에 있어야 해.
박사1편 9장의 규칙 채점기가 훈련실에서 하던 일을, 여기서는 업무 현장의 검증기가 하는 거지. 심판석의 규칙은 어디서나 같은 자리에 있어.
07

파이썬 실험 노트

numpy만 씁니다. 업무 8종, 성공 확률, 비용, "된 것 같아 보이는" 비율은 모두 설명을 위한 가정입니다. 헤르메스의 실제 내부 구현이 아니라, 스킬 저장 정책의 차이를 보여 주는 모형입니다.

skill_loop.py스킬 없음 · 자기 판단 저장 · 검증 후 저장
# 2편 5장 — 자가개선 루프 : 실행 예제 모음
# 상황: 주판봇이 매일 반복 업무 8종 중 하나를 에이전트에게 맡긴다. 숫자는 설명용 가정.
import numpy as np

TASKS = ["주간 시장 보고서", "장부 대사", "뉴스 요약", "고객 문의 답장",
         "환율 알림", "회의록 정리", "SEO 점검", "월말 정산표"]

def day_result(rng, skill):
    """스킬 상태에 따라 오늘 일의 성공 여부와 비용(토큰·시간)을 정한다."""
    if skill is None:                     p, cost = 0.55, 10.0          # 매번 처음부터 시행착오
    elif skill["bad"]:                    p, cost = 0.35, 6.0           # 잘못 배운 절차를 그대로 따라 함
    else:
        q = skill["q"]
        p, cost = 0.55 + 0.4 * q, 10.0 - 6.0 * q                         # 좋은 스킬일수록 빠르고 정확
    return rng.random() < p, cost

def simulate(policy, days=90, seed=0, snap=None):
    rng = np.random.default_rng(seed)
    skills, log = {}, []
    for d in range(days):
        if snap is not None: snap.append({k: dict(v) for k, v in skills.items()})
        t = int(rng.integers(len(TASKS)))
        sk = skills.get(t)
        ok, cost = day_result(rng, sk)
        looks_ok = ok or rng.random() < 0.3                              # 실패해도 30%는 "된 것 같다"
        if policy == "자기 판단으로 저장":
            if looks_ok and sk is None:
                skills[t] = {"q": 0.5, "bad": not ok}                     # 거짓 성공도 스킬로 굳어짐
            elif looks_ok and sk and not sk["bad"]:
                sk["q"] = min(1.0, sk["q"] + 0.1)
        elif policy == "검증 후 저장 + 실패 분석":
            if ok and sk is None:
                skills[t] = {"q": 0.5, "bad": False}                     # 검증을 통과한 절차만 저장
            elif ok and sk:
                sk["q"] = min(1.0, sk["q"] + 0.1)                         # 쓸 때마다 다듬음
            elif not ok and sk:
                if sk["bad"]: del skills[t]                               # 실패 분석: 틀린 스킬은 폐기
                else: sk["q"] = min(1.0, sk["q"] + 0.05)                  # 실패 원인을 스킬에 덧붙임
        log.append((ok, cost))
    return log, skills

print("[예제 1] 90일 동안의 결과 (같은 날 같은 일, 정책만 다름 · 200번 평균)")
print("  정책                      앞 30일 성공  뒤 30일 성공  뒤 30일 평균 비용  저장된 스킬")
for policy in ["스킬 없음", "자기 판단으로 저장", "검증 후 저장 + 실패 분석"]:
    first, last, cost, nsk, nbad = [], [], [], [], []
    for s in range(200):
        log, skills = simulate(policy, seed=s)
        first.append(np.mean([o for o, _ in log[:30]])); last.append(np.mean([o for o, _ in log[-30:]]))
        cost.append(np.mean([c for _, c in log[-30:]]))
        nsk.append(len(skills)); nbad.append(sum(v["bad"] for v in skills.values()))
    print(f"  {policy:22s}  {np.mean(first):8.1%}     {np.mean(last):8.1%}      {np.mean(cost):6.1f}"
          f"         {np.mean(nsk):.1f}개 (잘못된 것 {np.mean(nbad):.1f}개)")

print("\n[예제 2] 30일째 아침의 스킬 서랍 (같은 날짜, 두 정책 비교)")
for policy in ["자기 판단으로 저장", "검증 후 저장 + 실패 분석"]:
    snaps = []
    simulate(policy, seed=1, snap=snaps)
    drawer = snaps[30]
    label = lambda v: "잘못됨" if v["bad"] else f"q={v['q']:.1f}"
    items = [f"{TASKS[t]}({label(v)})" for t, v in sorted(drawer.items())]
    print(f"  {policy}: " + ", ".join(items))

사례와 한계

사례 · 주간 점검

매주 알아서 도는 감사

여러 웹사이트의 검색 노출 상태를 매주 확인하던 운영자가 헤르메스에게 맡겨, 매주 자동으로 전체 점검을 돌리고 추세 보고서를 텔레그램으로 받게 했습니다. 3장의 예약 루프와 이 장의 스킬이 함께 쓰인 예입니다.

브런치(2026.4)
사례 · 통합

다섯 에이전트를 하나로

4장 끝의 핀테크 창업자는 따로 놀던 에이전트 다섯 개를 헤르메스 하나로 합쳤습니다. 마케팅에서 쌓인 브랜드 말투가 영업에도 반영되고, 커뮤니티 피드백이 다음 날 마케팅 문구에 녹아들었다고 합니다. 기억과 스킬이 한곳에 모인 효과입니다.

GPTers(2026.4)
기업 도입

작업자와 운영 계층

기업 환경에서는 헤르메스를 "작업자"로 보고, 그 바깥에 권한·컨텍스트·감사 기록·검증·되돌리기를 담당하는 운영 하네스가 따로 필요하다는 시각도 있습니다. 2장의 겹겹 구조가 한 겹 더 늘어나는 셈입니다.

PuppyOne(2026.5)
한계와 쟁점무슨 뜻인가
새로운 개념인가스킬과 기억 파일은 개념적으로 다른 코딩 도구의 규칙 파일(사람이 직접 관리)과 크게 다르지 않고, 차이는 "누가 관리하느냐", 즉 자동화 수준에 있다는 평가가 있습니다.
정량 근거스스로 스킬을 추출하고 기억을 고르는 방식이 실제로 얼마나 잘 작동하는지에 대한 공개 벤치마크나 정량 비교는 부족하다는 지적이 있습니다.
결국 모델 체급?"여러 에이전트 프레임워크를 써 봤는데 차이를 못 느끼겠다", "결국 모델 체급이 중요하다"는 사용자 반응과, "같은 모델이라도 하네스에 따라 성능이 크게 달라진다"는 보도가 함께 존재합니다.
굳어진 오류5절의 교훈 2처럼, 검증 없이 쌓인 스킬은 잘못된 습관을 영구화할 수 있습니다.

정리와 다음 장 예고

이 장의 질문은 사실 이 시리즈 개요를 짤 때 나온 것입니다. "헤르메스의 '성공하면 스킬로 저장, 실패하면 분석'은 1편 4장의 강화학습과 어떻게 닮았나?" 고쳐지는 것이 어디에 있는지로 비교하면 이렇습니다.

어디서무엇이 고쳐지나무엇을 보고언제
1편 4장 강화학습점수표 Q(s,a)보상훈련 중
1편 8·9장 RLHF·추론 모델신경망 가중치사람의 선호 · 규칙 채점훈련 중
2편 3장 Reflexion한 일 안의 반성 메모검증 결과운용 중 (한 번의 일)
2편 5장 헤르메스스킬 파일 · 기억 파일일의 성공과 실패운용 중 (날과 세션을 넘어)
다음 장: 강화학습이 꿰는 실. 2편의 마지막 6장에서는 1편과 2편 전체를 한 번에 정리합니다. 훈련실의 강화학습이 어떻게 업무 현장의 루프로 옮겨 왔는지, 그리고 1편 1장의 플로우차트가 판단 → 채점 → 문지기 → 심판으로 자리를 옮겨 온 여정을 한 장의 지도로 그립니다.
